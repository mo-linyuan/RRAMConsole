# RRAM芯片控制台

面向不同系列 RRAM 芯片的控制台。顶部选择芯片系列，目前仅接入 **I1003 系列**，现有报文、寄存器、配方和执行逻辑均属于 I1003，不适用于尚未接入的其他系列。

I1003 通过 UDP 控制板卡 FPGA，再由 FPGA 把 64 位 PKG 送进芯片的 NoC，用来完成 RRAM 写测试（配 reg[8]、批量写指令、停止、启动、查结束）。

## 芯片系列与扩展

`run.py` 使用公共入口 `rram_console.app`；`rram_console/chips/` 注册芯片系列并提供系列后端。现有 I1003 模块与导入路径继续保留，避免破坏旧脚本。

后端负责创建自己的通信链路、执行器、路由栏、一键测试、报文模板及序列面板，也负责启动确认、收包解释和序列头信息处理。添加其他系列时，在独立模块中实现这些接口，再通过 `register_family(ChipFamily(...))` 注册；参考 `rram_console/chips/i1003.py`。只有实现并注册的系列才会出现在选择框中，不创建无法运行的占位型号。

不同系列可以使用完全不同的指令编码和执行流程；当前一键测试与模板仍是 I1003 专用界面。切换系列会加载对应后端、清空旧序列；连接或运行期间禁止切换。各系列设置分开保存，I1003 沿用原设置键名。

所有系列的 RRAM 阵列统一为 **128×128（16,384 个器件）**，规格集中定义在 `rram_console/hardware.py`；行、列编号均为 `0～127`。一键测试与 WRITEB 模板按此范围输入并校验，WRITEB 模板自动把行列转换成器件地址；旧模板中的 HEX 地址编辑时会兼容转换，保持原指令地址不变。

阵列尺寸与地址编码分别处理：I1003 的行列位域排列仍保留现有两种待确认编码，不能仅凭阵列尺寸确定。结构化序列导入与发送时拒绝无法映射到阵列的 WRITEB 地址。16,384 个器件不等于指令区容量，I1003 指令区仍为 8192 条，整阵列测试需要另行设计分批流程。

新导出的 JSON 序列头记录 `chip_family`，导入时校验与当前系列一致；旧文件未声明系列时按 I1003 处理。原始 HEX 不包含型号标识，不能自动推断其适用芯片。

## 运行

只用 Python 标准库，Python 3.8 以上即可。

```
python run.py                       # 启动调试台
python -m tools.fake_board          # 另开一个窗口：模拟板卡，离线调界面用
python -m unittest discover -s tests -t .   # 跑测试
```

运行前关掉网络调试助手，两个程序不能同时占用本机 8080 端口。电脑有线网卡要设为 192.168.1.9，FPGA 的回包固定发往 192.168.1.9:8080。

用模拟板卡时，调试台里把本机设成 `127.0.0.1:9081`，板卡设成 `127.0.0.1:9080`。加 `--no-chip-reply` 可以模拟现在真实板卡"芯片不回包"的情况。

界面设置自动保存在 `~/.i1003_console/settings.json`。

## 执行结果与实验记录

- **先检查再发送**：启动前检查整个任务，拒绝越界地址、溢出数据、负数或无效等待时间，避免发到一半才发现后续参数有误。
- **核对失败就停止**：勾选的 reg[8]、首条指令核对，遇到超时或数据不一致立即中止后续步骤。未收到结束回包也判为失败。纯发送成功只显示“已发送”，不代表芯片执行成功。
- **统一读操作**：原始 HEX 的单帧读请求、FPGA 模板读请求和芯片读请求都会等待匹配回包；写操作不会自动重发。
- **过滤无关回包**：仅目标板卡 IP/端口的报文可以用于应答；芯片回包按 send-out 类型、地址和反向源/目标坐标匹配。未匹配或其他来源的包仍显示并记录，但不用于核对。回包格式与真实芯片的兼容性仍须实测；协议没有事务编号，同一请求的迟到回包无法完全消歧。
- **明确任务状态**：左下序列显示运行进度、核对结果、失败与停止状态；运行期间禁止增删、移动、替换或导入序列。任务使用启动时的参数快照。单条发送间隔也作用于批量指令逐帧发送。
- **停止发送**：立即唤醒软件等待并停止后续发送；已经启动的芯片操作不会自动终止，当前未实现芯片级紧急停止指令。“UDP 已打开”仅表示本地通信链路已打开，芯片状态需查询确认。

每次运行自动创建 `~/.rram_console/runs/*.jsonl`，包含芯片系列、端点、路由和运行选项、完整序列、完整 TX/RX 字节、UTC 时间戳、相对时间、步骤状态及最终结果。日志标题栏的“运行记录”按钮可打开目录。“保存”仍用于导出当前可见文本日志；清空可见日志不删除运行记录。

记录逐事件刷新，异常退出时可保留已写出的内容；只有带最终 `finished` 事件的文件才能视为正常收尾，不能把不完整记录当成成功。记录创建失败时不启动任务；运行中记录写入失败会显示错误，已有任务继续执行。文件不会自动清理，可自行备份或删除。

新增系列后端可实现 `run_metadata(items, options)` 提供自己的序列及参数序列化；控制台负责公共记录格式，各系列负责自身命令和读回规则。离线模拟测试只证明软件逻辑，不等于真实芯片验证。

## 目录结构

```
i1003/
  protocol/       协议层：纯函数，不依赖任何其他模块
    fpga.py         FPGA 帧格式和地址定义（依据 common_reg.sv、decode.v）
    pkg.py          NoC 64 位 PKG 编解码、路由 Route
    isa.py          指令编码（WRITEB、停止指令）、reg[8] 写验证配置、10 MHz 时序换算
  transport/
    udp_link.py     UDP 收发、请求与回包配对、查芯片 Ready
  model/
    items.py        序列条目：每种条目知道怎么展开成帧、怎么序列化
    sequence_io.py  导入导出：本项目 .json、网络调试助手 .ini、纯文本
  engine/
    runner.py       按序列执行，事件通过 RunEvents 回调报告，不碰界面
  recipes/
    write_test.py   RRAM 写测试配方：WriteTestSpec → 序列条目 + 摘要
  ui/             界面层
    theme.py        颜色、字体、样式
    context.py      面板之间的接口（AppContext）
    templates.py    报文模板的数据定义
    settings.py     设置保存
    app.py          主窗口：组装各部分，实现 AppContext
    panels/         各面板，只依赖 AppContext，互不引用
tests/            单元测试 + 界面冒烟测试
tools/fake_board.py   模拟板卡
run.py
```

依赖方向是单向的：`protocol ← transport ← engine`，`protocol ← model ← recipes`，`ui` 在最上层。除 `ui` 外都不 import tkinter，所以协议、配方、执行器都能脱离界面单独测试和复用，比如以后写批量测试脚本时直接用 `recipes` + `engine`。

### 常见改动应该改哪里

| 想做的事 | 改哪里 |
|---|---|
| FPGA 加了新地址（比如复位寄存器） | `protocol/fpga.py` 的 `Addr`，再在 `ui/templates.py` 加一个模板 |
| 确认了行列在器件地址里的排法 | `protocol/isa.py` 的 `CellEncoding` |
| 确认了源节点坐标或 RGN | `ui/panels/toolbar.py` 里 `RouteBar` 的默认值，或 `protocol/pkg.py` 的 `Route` |
| 芯片时钟不是 10 MHz | `protocol/isa.py` 的 `CHIP_CLK_HZ` |
| 新增一种测试流程 | 在 `recipes/` 下新建配方，返回 `List[Item]`，界面只需加按钮调用 |
| 新增一种条目（比如等外部触发） | `model/items.py` 加类，`engine/runner.py` 加执行分支 |

## 选通参数

板上 BL、SL、WL 的电压接 4200 的 SMU，芯片在脉冲期间把选中的器件接进回路。一键测试沿用师姐的原始参数输入：基时间 254、时间倍数 255、验证次数 0、重复 4095 次，直接生成 `reg[8] = 00FF_00FE`。界面不再按选通秒数反推次数。

当前 FPGA 的芯片时钟固定为 10 MHz；软件显示该频率，并在详细参数中换算脉宽和名义累计时间，界面不能调整实际硬件时钟。重复 WRITEB 是否在指令边界存在关断间隙，需要实测。指令区共 8192 条，预留一条停止指令后最多写 8191 条 WRITEB。

“重复次数”右侧实时显示总选通时间（名义）：`基时间 × 时间倍数 ÷ 10 MHz × 每器件重复次数 × 器件数`，并分别显示单次脉宽和每器件累计时间。该值只累计配置脉宽，不计验证重试、指令间隙、通信及软件等待，不代表实测的连续选通时间。参数无效时显示 `—`。

## 从 FPGA 工程确认的事实（I1003_NOC_1012）

| 报文 | 作用 |
|---|---|
| `00 01` / `80 01` | 读 / 写 `noc_in_ready`（FPGA 是否接收芯片输出），复位为 1。同事给的"初始使能"其实是读 |
| `00 02` | 读芯片 `pad_Noc_i_3_Ready` |
| `80 03` / `00 03` | 发 PKG 给芯片 / 读回 FPGA 最后发出的 PKG |
| `00 04` / `80 04` | 读 / 写芯片 `boot_mode` 引脚，复位为 1 |
| `80 00` | **禁止**：bit63 会打开以太网测速模式 |

- 给芯片的时钟都是 10 MHz（RTC 为 6.52 MHz）。
- 芯片输出：FPGA 检测 `noc_in_valid` 上升沿，把 64 位包以 8 字节 UDP 包发给电脑。
- 一个 UDP 包里可以有多帧，decode 逐帧处理（"批量快速发送"依赖这一点）。

## 待确认 / 待修改

- `por_rst_n`、`sys_rst_n` 在 FPGA 里接成常数 1，芯片从未被复位。这是芯片不回包的头号嫌疑，建议 PLL 锁定后再释放，并加一个可由电脑触发的复位地址。
- `noc_out_valid` 固定拉高 10 个周期、不等握手，同一个包可能被芯片接收多次。
- 源节点 30、RGN=0 是推断；回包要回到片外口，需要哪种 RGN/HEADER 手册没写。
- 器件地址里行、列的排法未确认（界面里两种都可选，只测第 0 行时没有区别）。
- 写验证"验证次数"大于 0 时芯片的实际行为未确认，I1000 实验台用的是 0。
