# 下载耗时、指令槽地址与器件地址核对

## 可核对的地址事实

`55 D5 80 03 05 C0 0F FA 40 00 00 02` 中：

| 字段 | 含义 | 核对依据 |
| --- | --- | --- |
| `55 D5` | PC报文头 | 现有FPGA decode及PC通信说明 |
| `80 03` | 写FPGA地址3，后续8字节为NoC PKG | 现有FPGA common_reg及通信说明 |
| `05` | PKG TYPE=5，写指令存储器 | I1003手册PKG字段 |
| `C0` | 源30、目标00 | 当前Route设置，不代表已实测路由正确 |
| `0F FA` | 指令槽地址4090 | PKG ADDR字段；与器件地址是两个字段 |
| `40 00 00 02` | WRITEB：PE0、TYPE0、阵列0、器件地址2 | I1003 WRITEB位域；I1000流程的第0行第2列示例 |

I1003部分手册开头列出指令存储器8192×32、13比特寻址。旧工程
`D:/DataCenter/FPGA/I1000_0907/I1000_0907/I1000_0907.srcs/sources_1/imports/new/sys_top.sv`
第107行给出 `long_tx_addr = long_cfg_num + long_tx_addr_init`，数据使用独立的 `long_tx_data`。
因此“固定指令字、递增指令槽”与旧long_tx生成方式一致，不能单凭地址递增认定切换了RRAM器件。

当前4095次配方写入0x0000～0x0FFE的4095条WRITEB，在0x0FFF写STOP `70F00000`，再单独写reg[0]=1。
WRITEB格式本身没有重复次数字段；软件目前沿用展开方式，没有未经验证地改成芯片循环指令。

这些事实不证明I1003板上NoC接收、PC取指、初始化、器件选通或Forming电气条件正确。
旧long_tx来自I1000直连测试总线工程，不能当作I1003整条控制链已测通的证据。
Forming在当前流程中使用TYPE0的RESET类指令，没有独立Forming操作码；实际操作依赖外部4200条件。

## 软件耗时修复

用户记录4096条下载126.941秒，约31ms/条。在用户运行的Anaconda Python3.14环境中，20次
`Event.wait(.02)` 实测约0.621秒，20次 `sleep(.02)` 约0.407秒，旧下载循环的20ms等待被放大。

下载间隔已独立为默认0，控制报文间隔仍保留20ms。非零短间隔使用分段sleep与取消标志。
既未修改FPGA工程，也未增加固件寄存器或把多帧UDP打包设为默认。

`python -m tools.profile_download` 仅连接本机127.0.0.1，使用完整逐帧JSONL记录：

- Ready关闭：4096条下载约0.383秒，模拟端收到4096条及末尾读请求，STOP槽读回一致。
- Ready开启：约1.182秒，模拟端收到4096条指令、4096次Ready查询及末尾读请求。

测量值记录于 `artifacts/download-timing.json`，不是实际板卡吞吐或接收完整性的验证。
4095次脉冲的名义累计26.523315秒与下载速度独立，该换算仅显示，不再自动生成预计执行等待。

## 停止的范围

“停止任务”取消后续发送、Ready/读回等待与软件预计等待。按钮点击测试覆盖这三个阶段，
并验证停止下载后没有发送序列后面的启动报文。完成与状态事件优先于文本日志处理。
该按钮不撤回已发出的UDP报文，不伪称芯片级急停。
